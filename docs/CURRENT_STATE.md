| 단계 | 내용 | 상태 |
|---|---|---|
| PR1 | AI 되묻기(follow-up questions) 기능 | ✅ 머지·배포 완료 |
| PR2 | 최종 결과 생성 API 신설(Sonnet, 4블록 스키마) + 레이트리밋 | ✅ 머지·배포 완료 |
| PR3 | 결과 화면에 4블록 추가(기존 지도는 유지, 그 아래에 얹음) | ✅ 머지·배포 완료 |
| PR-A | (추가 개선) 2x2 매트릭스 라벨 겹침 해결 | ✅ 머지·배포 완료 |

## 현재 마일스톤: "이상형 MAP + 익명 공유 링크"

위 "결과 중심 구조 전환"과 별개로 진행된 트랙입니다. 종류(주제) 선택 화면에서 "이상형"을 고르면 대화 대신 퀴즈형 입력을 받아, 7요소(기준·끌림 패턴·매트릭스·신호등·자기 성찰·로드맵 등) 구조의 결과 카드를 시각 블록으로 보여줍니다. 여기에 로그인 없이 결과를 지인에게 공유할 수 있는 익명 링크 기능을 얹었습니다.

| 단계 | 내용 | 상태 |
|---|---|---|
| - | 이상형 MAP 입력 UI + 결과 생성·시각화(7요소 구조, 텍스트→시각 블록) | ✅ 머지·배포 완료 |
| 1단계 | 공유 링크: Upstash Redis 연결 + 이상형 공유 API(하루 5회 제한, 90일 자동 만료) | ✅ 머지·배포 완료(PR #67) |
| 2단계 | 공유 링크: `/r/{id}` 읽기 전용 뷰(검색엔진 노출 차단) | ✅ 머지·배포 완료(PR #68) |
| (보강) | 저장소(Redis) 장애 시 "만료됨"이 아니라 "일시적 문제"로 구분해 안내 + 고정 OG 미리보기 이미지 | 🔎 Draft PR #69 — 오너 검증 대기 중 |
| 3단계 | 개인정보처리방침 갱신(서버 저장 사실·90일 보관·Upstash 국외 이전 가능성 고지) | ⏸️ **미착수 — 공유 기능을 실제로 켜기(오너가 Vercel에서 Upstash 연결) 전 필수** |

공유 링크에 저장되는 데이터는 결과 JSON뿐이며, 대화 원문(messages)·IP·이메일은 저장하지 않습니다(IP는 하루 공유 횟수 제한을 위해 별도 키에 24시간만 임시로 씁니다). 지금은 오너가 아직 Vercel에서 Upstash를 연결하지 않아, 프로덕션에서는 "지금은 공유 링크를 만들 수 없어요" 안내만 뜨는 안전한 상태입니다.

## CI / 브랜치 보호 · 머지 방식

- `.github/workflows/quality-gate.yml`("MAP Quality Gate")이 모든 PR에서 `typecheck`, `harness:check`, `design:check`, `build`를 실행하며, GitHub의 필수 상태 체크로 등록되어 있습니다.
- `.github/workflows/auto-merge.yml`("Guarded Auto Merge")이 Quality Gate 성공 시 **브랜치 이름과 무관하게 모든 PR을 자동으로 `main`에 스쿼시 머지**합니다. `chore/`와 `feature/`를 구분해 수동 머지하던 과거 정책은 더 이상 적용되지 않습니다 — 오너가 확인할 유일한 사람 검증 기회는 PR을 열기 전(또는 머지되기 전) 직접 화면을 보는 것뿐입니다.
- `main`은 PR을 통해서만 반영됩니다.

## 배포 · 모니터링

- `main`에 머지되면 Vercel이 자동으로 프로덕션에 배포합니다.
- `.github/workflows/production-smoke.yml`("Production Smoke Check")이 (1) `main` 푸시 시, (2) Guarded Auto Merge 성공 직후, (3) 6시간마다(cron) `mapdecision.com`이 정상 응답하는지 확인하고, 실패하면 GitHub 이슈를 자동 생성합니다.
- `.github/workflows/notify-n8n-on-merge.yml`이 머지될 때마다 n8n 웹훅으로 커밋 정보를 전달합니다. n8n 쪽에서 이 웹훅을 어떻게 처리하는지(알림 주기·채널 등)는 n8n 클라우드에 설정된 워크플로 내용이라 이 레포에서는 확인할 수 없습니다.
- **n8n Cloud 무료 체험이 실행 횟수를 소진해 곧 종료됩니다** — 그동안 n8n이 하던 헬스체크·일일 생성 한도 알림을 `.github/workflows/health-check.yml`, `.github/workflows/daily-limit-alert.yml`(GitHub Actions)로 옮겼습니다. 위 머지 알림(notify-n8n-on-merge.yml)은 이번 이전 범위에 포함되지 않았습니다.
- 이 개발 샌드박스는 네트워크 프록시로 `mapdecision.com`에 직접 접근이 막혀 있어, 배포 확인은 위 GitHub Actions 결과(간접 증거)로만 합니다.

## AI / 안전장치 현황

- 대화 중 노드 추출과 되묻기(follow_up_questions)는 Haiku 4.5, 최종 결과 생성/블록 재생성은 Sonnet 5를 사용합니다. 두 경우 모두 `ANTHROPIC_API_KEY`가 없으면 대화는 규칙 기반(`local-conversation-provider`, `extractThinking`)으로 조용히 대체되지만, **최종 결과 생성은 규칙 기반 대체 결과가 없고 그냥 실패 처리됩니다** (아래 리스크 참고).
- 레이트리밋:
  - 하루 세션 시작 5회/IP (`registerSessionStart`) — 인메모리, 서버리스 재시작 시 초기화되는 느슨한 안전핀(AI 호출 비용이 사실상 없는 가벼운 동작이라 그대로 둠).
  - 대화 메시지 40개/세션, 입력 5,000자/메시지.
  - 최종 결과 생성(전체+블록 재생성 합산): 세션당 5회, IP당 하루 10회, **서비스 전체 하루 상한**(`DAILY_GLOBAL_GENERATION_LIMIT` 환경변수, 기본값 300 — IP·세션과 무관해 IP 로테이션으로 못 뚫음). 전부 Upstash Redis 원자적 `INCR`+`EXPIRE`로 이전(아래 리스크 7번 해결 완료).
  - 생성 API(`/api/generate-idealtype-result`, `/api/generate-result`)에 Origin/Referer 검사 추가 — curl 한 줄로 직접 때리는 기회주의적 남용을 막음(위조 자체는 못 막음, 헤더를 아예 안 보내는 가장 흔한 경우만 차단).
  - 사용자 발화 3턴 미만이면 최종 생성 자체를 차단.
- 법적 고지: `/privacy`, `/terms` 페이지와 AI 전송 고지 문구가 배포되어 있습니다(실무 참고용 초안이며 법률 자문 아님, 오너 확인 필요 문구 포함).

## 주요 미해결 리스크

1. **최종 결과 생성 실패 시 폴백이 거칠다.** `ANTHROPIC_API_KEY`가 없거나 Sonnet 호출이 실패하면 "지금은 결과를 생성할 수 없어요"라는 일반 메시지만 뜨고, 원래 설계에서 계획했던 "AI 연결 없음을 명시하고 규칙 기반 간이 결과라도 보여주는" 폴백은 아직 구현되지 않았습니다. 실패와 "AI 자체가 꺼져 있음"이 사용자 입장에서 구분되지 않습니다.
2. **4블록 결과의 실제 품질이 검증되지 않았습니다.** 이 개발 환경에 API 키가 없어 문장 품질, closest_fit 판단의 타당성, 톤(상담처럼 느껴지는지) 등을 실제로 확인한 적이 없습니다.
3. **결과 캐시와 대화의 불일치.** 결과 화면을 한 번 본 뒤 대화로 돌아가 더 말하고 다시 결과 화면에 오면, 자동으로는 예전 결과가 그대로 보입니다(블록별 "다시 생성" 버튼으로 수동 갱신은 가능).
4. **Bible §2/§6과 코드의 불일치.** 위 "제품 정의 기준 문서" 항목 참고 — PR4 전까지 의도적으로 남아있는 상태입니다.
5. **매트릭스 라벨 겹침은 8개 상한 안에서만 검증됨.** 요인이 8개를 넘는 경우는 스키마에서 막혀 있어 실제로 발생하지 않지만, 8개에 가까운 극단값에 대한 자동 테스트는 없습니다(수동 스크린샷 검증만 거침).
6. **개인정보처리방침이 공유 링크 기능을 아직 반영하지 않았습니다.** 서버에 결과가 저장된다는 사실, 90일 보관, Upstash를 통한 국외 데이터 이전 가능성이 고지에 빠져 있습니다 — 위 "이상형 MAP + 익명 공유 링크" 3단계에서 갱신 예정이며, 그 전까지는 오너가 Upstash를 연결하지 않는 것으로 실제 위험을 차단하고 있습니다.
7. ~~레이트리밋이 인메모리라 구멍이 세 가지 있습니다.~~ **해결됨(2026-07-27).** 생성 레이트리밋을 Upstash Redis 원자적 연산(`INCR`+`EXPIRE`, KST 자정 기준 초기화)으로 이전했습니다(`src/map-decision-v1/engine/rate-limit.ts`의 `reserveGenerationSlot`/`releaseGenerationSlotOnFailure`). 기존 세 가지 구멍 중:
   1. **다중 인스턴스 문제 — 해결.** Redis가 단일 진실 공급원이라 인스턴스가 여러 개여도 카운터가 하나로 합쳐집니다.
   2. **동시 요청 우회 — 해결.** 조회 후 나중에 차감하던 방식 대신, 원자적 `INCR`로 먼저 자리를 "예약"하고 초과분은 즉시 롤백하는 방식으로 바꿨습니다 — 동시에 여러 요청이 들어와도 한도를 넘어 통과할 수 없습니다(15개 동시 요청·상한 6 조건에서 정확히 6개만 통과하는 것을 Playwright로 확인).
   3. **`session.startedAt` 위조 — 미해결(설계상 남아있음).** 세션 키 자체는 여전히 클라이언트가 보내는 값이라 위조 가능합니다. 대신 생성 API에 Origin/Referer 검사를 추가해 "curl 한 줄" 같은 기회주의적 직접 호출을 막았습니다 — 다만 Origin/Referer 자체도 위조 가능해서, 작정하고 헤더까지 위조하는 공격자에게는 여전히 뚫립니다. 이 경우 최종 방어선은 (a) IP당 하루 10회, (b) 서비스 전체 하루 상한(`DAILY_GLOBAL_GENERATION_LIMIT`, IP·세션과 무관해 로테이션으로 못 뚫음)입니다.
